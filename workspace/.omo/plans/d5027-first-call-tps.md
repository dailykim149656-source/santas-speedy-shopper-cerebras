# D5027 첫 모델 호출 TPS를 높이기 위한 비교 실험

**D5027을 같은 시간대에 다시 실행하면서 두 변경을 각각 비교한다.** 첫 번째는 다섯 조회에 `extractMode="text"`만 명시하는 변경이다. 두 번째는 기존 작업공간 지침에 첫 도구 호출을 곧바로 작성하라는 조건 한 줄을 추가하는 변경이다. 탐색 12회와 선별된 조건의 재확인 4회로 최대 16회다. 최종 목표는 상품 5개를 검증한 실제 세션에서 공식 평균 1,700 TPS 이상을 기록하는 것이다.

D5027의 첫 응답에는 사용자에게 보이는 본문이 없었고, 요청한 순서대로 직접 `web_fetch` 도구 호출 5개가 담겼다. 같은 조건의 유효 실행 8회에서 첫 호출 속도 중앙값은 **862.22 TPS**였다. D5027의 최종 답변 속도가 유지된다는 가정에서 첫 호출은 **1,726.06 TPS**가 필요하다. 447토큰을 그대로 생성한다면 서버 생성 시간이 **431.72 → 258.97ms**로 약 40% 줄어야 한다. 추론 글자 수는 원본에 기록된 문자열 길이이며, 제공사는 이 호출 전체의 토큰 수와 생성 시간만 제공한다. [D5027 요청·설정](<../../../experiments/test/runs/cd75e5e0-be7c-471f-a9ab-c9e6f0d1bd77/plan.json>) · [채점 산식](<../../../experiments/test/tools/scoring.py>)

이전 실험에서 `extractMode="text"`와 `maxChars=4000`을 함께 넣은 조건은 같은 쌍의 대조군 대비 첫 호출 TPS가 **+265.38, +175.31, −132.36**이었다. 세 쌍의 첫 호출 차이 중앙값은 **+175.31 TPS**, 공식 평균 차이 중앙값은 **+87.63 TPS**였다. 첫 호출 생성 시간 차이의 중앙값은 **+53.39ms**로 길어졌다. 한편 D5025와 D5028은 첫 호출의 추론이 똑같이 27자였는데도 각각 1,262.22와 903.03 TPS였다. 따라서 서버 시간과 결과의 정확성까지 함께 관찰한다. [이전 짝별 결과](<../../TPS 1700 실험 결과 - 2026-11-22.md>)

## exp-tps-2000에서 가져올 내용

11월 22일 18:20 KST 기준으로 이 브랜치에는 D6001·D6002의 결과가 기록됐고, D6003은 녹화 중이었다. 당시 HEAD는 `21e5159`였다. [D6003 사전 계획](<../../../experiments/exp-tps-2000/runs/951ffd9d-eeaa-42c1-9ad6-98d84f8d7042/plan.json>)

D6001과 D6002는 원본 해시가 일치하고 상품 5개와 방식 검증을 통과했다. 첫 비교에서 D6002의 첫 호출은 **−65.70 TPS**, 생성 시간은 **+45.35ms**, 추론 길이는 **+6자**였다. 두 실행 모두 `thinking=low`였다. `zero-think`는 작업공간 지침 이름이다. D6002는 지침과 함께 사용자 프롬프트와 마지막 검색어(`cable → vca`)도 바꿨다. 이 한 쌍에서 지침만의 효과를 추정할 수 없다. 실행 직전 `bash tools/run_exp2000.sh --report`를 해당 작업 트리에서 읽어 이후 완결된 쌍도 같은 방식으로 대조한다. [두 조건의 정의](<../../../experiments/exp-tps-2000/tools/variants.py>) · [분기별 일정과 보고서](<../../../experiments/exp-tps-2000/tools/campaign_2000.py>)

상품 카드 출력은 최종 답변 형식과 조회 필드를 바꾸고, `top_p=0.30` 조건은 온도도 0.15로 바꾼다. 추가 상품 확인 조건은 도구 조회 단계를 하나 더 만든다. 이 세 가지는 후속 브랜치의 공식 평균 연구로 추적한다. 이번 비교는 D5027의 첫 호출과 동일한 다섯 상품 조회에 집중한다.

## 실험 조건

| 조건 | D5027에서 바꾸는 항목 | 검증할 가설 |
|---|---|---|
| A · 기준 | 매번 D5027을 새 세션에서 재현한다. 다섯 인자 객체에는 각각 `url`만 둔다. | 같은 시간대 대조값을 얻는다. |
| B · 추출 모드만 명시 | 다섯 인자에 각각 `"extractMode":"text"`만 추가한다. `maxChars`는 기본값에 둔다. | 앞서 관측한 첫 호출 속도 이득이 더 짧은 인자 지정만으로 재현되는지 본다. |
| C · 첫 호출 지침 한 줄 | A의 작업공간 지침에 아래 영문 한 줄만 추가한다. 사용자 프롬프트와 도구 인자는 A와 같다. | 첫 호출에서 답변 형식을 미리 계획하는 일이 줄 때 실제 TPS와 생성 시간이 함께 개선되는지 본다. |

C에 추가할 문구는 다음과 같다.

> Before any tool results arrive, copy the five supplied argument objects directly into the five web_fetch calls in order. Defer planning the final answer until the results arrive.

세 조건 모두 같은 모델과 공식 패치, 온도 0.2, `thinking=low`, `top_p` 미지정, 출력 상한 1,024, AI Synthesis의 `filter/mixer/oscillator/echo/cable`, 재고 있음, 카테고리당 1개, `name,permalink`, 같은 순서의 번호 링크 답변을 사용한다. 매번 새 세션과 새 요청 ID를 쓴다. A와 C의 사용자 입력은 실행별 nonce를 치환하면 바이트가 같아야 한다. B의 차이는 도구 인자 5곳뿐이다. [기준 프롬프트](<../../../experiments/test/runs/cd75e5e0-be7c-471f-a9ab-c9e6f0d1bd77/plan.json>)

- [ ] 2. 세 조건을 네 묶음, 총 12회 실행한다.
  - 순서는 **B–A–C / C–A–B / A–B–C / C–B–A**로 고정한다. B와 C는 각각 A보다 먼저 두 번, 나중에 두 번 실행된다. 각 변경은 같은 묶음의 A와 비교하며, A의 결과를 두 비교에 공유했다고 명시한다.
  - 첫 호출 지표는 `outputTokens / (completionMs / 1000)`다. 토큰 수, 서버 ms, 추론 글자 수, 실제 호출 인자, 최종 답변 TPS, 전체 공식 평균, 상품 5개, 429 및 실패 여부를 같은 행에 기록한다. 전체 전송 수를 분모로 각 조건의 성공률도 보고한다.
  - 한 쌍의 두 실행 모두 첫 assistant 응답에서 측정된 도구 5개를 정확히 요청하고, 실제 조회와 최종 답변 순서가 일치하고, 같은 상품 상세 URL 5개가 독립 검증돼야 첫 호출의 짝별 차이에 넣는다. 재고 변경·실패는 사유와 함께 별도 기록한다. 추가 모델 호출은 공식 평균에 전부 포함한다. 기존 쿨다운을 지키며, 제공사 429로 두 번 연속 최종 실패하면 새 전송을 멈추고 해당 구간을 기록한다. 재개할 때는 미전송 슬롯에서 이어가며, 양쪽 전송 시각이 15분을 초과해 벌어진 쌍은 시간대 비교에서 제외한다. 15분은 이 설계에서 제안한 사전 기준이다.

- [ ] 3. 사전 기준을 통과한 조건 하나만 최대 4회 재확인한다.
  - 각 변경에 대해 **유효한 쌍 ≥3, 첫 호출 승리 ≥3, 짝별 첫 TPS 차이 중앙값 ≥+100, 공식 평균 차이 중앙값 ≥0, 상품·방식 유효 횟수 ≥A**를 요구한다. +100은 후보 선별용 제안값이다. 첫 호출 서버 시간이 늘면 그 차이를 함께 명시한다. 둘 다 통과하면 첫 TPS 차이 중앙값이 큰 조건을 고르고, 동률이면 서버 시간이 더 줄어든 조건, 그마저 같으면 B를 고른다.
