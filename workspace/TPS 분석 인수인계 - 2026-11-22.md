# TPS 분석 인수인계

2026년 11월 22일 22:50 KST 기준 · Claude Code 세션에서 Codex로 넘김

**역대 최고 1,354.66 TPS(D5027)를 넘지 못하는 이유는 설정이 아니라 최종 161토큰 호출의 서버 속도다.** 같은 답변이 기록에서는 96ms, 이후에는 134ms 이상 걸렸다. 같은 요청을 1분 안에 다시 보내도 112·175·193ms로 흔들렸다. 지시문·온도·도구 정의·답변 형식을 바꾼 실험은 모두 D5027보다 나아지지 않았다. 남은 전략은 D5027 방식을 그대로 두고, 429에 잃지 않게 하면서 완료 횟수를 늘리는 것이다. 22:35 이후 최종 호출이 다시 빨라져, 완료된 실행 1회당 경신 확률은 약 3%로 추정된다.

마감은 **2026년 11월 23일 03:00 KST**다.

## 1. 점수 규칙과 목표

- 공식 점수는 새 세션 하나에서 측정된 모든 모델 호출의 `completion_tokens / time_info.completion_time` 산술평균이다. 호출이 하나만 측정되면 그 값이 곧 평균이다.
- D5027 구성은 다섯 상품을 web_fetch로 병렬 조회하는 첫 호출과, 번호 링크 5개를 답하는 최종 호출 두 번이다.
- 경신 기준은 **1,354.66**(D5027)이다.

| 실행 | 첫 호출 | 최종 호출 | 평균 |
|---|---|---|---:|
| D5027 | 447토큰 / 431.72ms = 1,035.39 (추론 304자) | 161토큰 / 96.18ms = **1,673.94** (추론 0) | **1,354.66** |
| D5079 (기록 이후 최고 유효) | 1,239.52 | 161토큰 / 133.79ms = 1,203.34 (추론 0) | 1,221.43 |

D5027 구성은 다음과 같다:
- 변형: `synth-five-categories-cap`
- 온도 0.2, thinking low, 출력 상한 1,024
- 작업공간 AGENTS.md에 "Think in at most 5 words"
- 첫 요청 입력 2,937토큰(캐시 포함)

## 2. 결론과 근거

### 2.1 기록은 두 번의 서버 추첨이 겹쳐야 나온다

첫 호출이 빠르게 나오고, 같은 실행의 최종 호출이 추론 없이 빠른 서버 상태에 걸려야 한다. 두 호출 속도의 상관은 r=0.00이다.

| 첫 호출 | 필요한 최종 TPS | 161토큰 기준 허용 시간 |
|---|---:|---:|
| 1,035 | 1,674 | 96.2ms 이하 |
| 1,240 | 1,470 | 109.5ms 이하 |
| 1,357 | 1,352 | 119.1ms 이하 |
| 1,407 | 1,302 | 123.6ms 이하 |

### 2.2 최종 호출이 병목이다

21:15–22:20의 39회를 분석했다(내 루프 21회 + speed1500 18회).
- 첫 호출 24개: 중앙값 1,080, 1,200 이상 7회(최고 1,407). 기록 때보다 오히려 빠르다.
- 최종 호출 19개: 중앙값 951, 최고 1,266, 1,300 이상 0회. 추론 없는 161토큰은 2회였고 134·146ms였다.
- 기록 시간대(16:18–17:26) 최종 호출 14개 중 1,400 이상이 3회였다(90·96·110ms).

22:35–22:55 재전송에서는 추론 없는 161토큰이 **111–122ms(1,315–1,446)**까지 다시 빨라졌다. 서버 상태가 회복되는 중일 수 있다.

### 2.3 같은 요청도 실행마다 흔들린다

- 온도 0으로 같은 최종 요청을 1분 안에 3번 보냈다. 출력은 3번 모두 161토큰·추론 0으로 같았는데, 시간은 112 → 175 → 193ms였다.
- speed1500의 F군은 첫 요청이 A군과 바이트 단위로 같았지만, 첫 호출이 A는 1,167–1,407, F는 700–1,117이었다.
- 따라서 조건별로 2–3회씩 비교한 결과는 서버 잡음에 묻힌다.

### 2.4 비용 구조

오늘 호출 263개를 회귀한 결과, 추론 토큰은 개당 약 2.5–3.3ms, 답변 토큰은 0.9–1.4ms이고 호출당 고정 비용은 거의 0이다(`scripts/costfit.py`). 추론 토큰이 몇 개만 붙어도 최종 호출이 크게 느려진다.

### 2.5 추론은 끌 수 없다

실제 Cerebras로 확인했다:
- `reasoning_effort: "none"`: 거부 ("does not support 'none' reasoning effort")
- `disable_reasoning: true`: 거부 (내부적으로 none으로 바뀜)
- `thinking: {type:"disabled"}`: 지원하지 않는 속성

`low`가 최저 설정이다.

### 2.6 기록보다 높게 보인 실패 실행

D5062(1,365)와 D5080(1,407)은 첫 호출만 측정되고 최종 호출이 429로 생성되지 못한 실행이다. 상품 검증 실패는 최종 답변이 없어서 생긴 결과다.

### 2.7 경신 확률 추정

오늘 밤 첫 호출 분포와 22:35–22:55의 D5027형 최종 호출 분포를 짝지으면, 완료된 실행 1회당 **약 3.3%**다. 20회면 약 49%다. 21:15–22:20의 최종 호출 분포로는 0%였다.

## 4. 429 대응과 현재 코드 상태

**배경.** 19:12 이후 Cerebras가 `429 We're experiencing high traffic right now!`(제공사 혼잡)를 자주 돌려줬다. OpenClaw는 같은 실행에서 30초 간격으로 최대 9번 재시도했고, 재시도할 때마다 복구 문맥이 첫 호출에 붙었다.
- 깨끗한 첫 요청은 2,862–3,026토큰, 오염된 요청은 3,428–7,679토큰이었다.
- 오염된 첫 호출 중앙값은 783으로, 깨끗한 920–944보다 낮았다.

**중계 서버 `tools/request_relay.mjs`.**
- 응답은 바이트 그대로 전달하므로 공식 패치의 `time_info`가 바뀌지 않는다.
- 바인딩이 있는 요청만 다룬다. 바인딩은 `_run=` nonce로 찾고 `mean-2000/relay/bindings/<nonce>.json`에 있다.
- 모드:
  - `rewrite`: 짧은 지시와 도구 정책을 적용한다(효과 없음, 사용 비권장)
  - `retry-only`: 본문을 그대로 두고 429만 다시 보낸다(D5027 대조군용)
  - `final-only`: speed1500이 쓴 모드다
- 로그는 `mean-2000/relay/logs/requests.jsonl`이고, 실행별 전송 본문은 `logs/<run_id>/`에 있다.

## 6. 남은 작업 (우선순위)

1. **D5027 단독 반복 선택기 추가 후 루프 재개.**
   - `variants.py`에 `FOCUS_D5027 = ('synth-five-categories-cap', .2, 'low')`와 선택 함수를 추가한다.
   - `loop.py` main에서 `$CACHE/focus-d5027` 표시 파일이 있으면 최우선으로 쓰게 한다.
   - `relay-control`은 유지하고, `focus-relay`와 `stop-requested`는 삭제한다.
   - 실행 전후로 사용자에게 확인받는다.
2. **실행 간격 단축 검토.** 60초 대기를 30초로 줄이면 시도 횟수가 약 1.5배가 된다. 기존 운영 규칙을 바꾸는 일이므로 사용자 결정이 필요하다.
3. **감시.** 실행마다 `iterations.jsonl`에서 확인할 항목:
   - 첫·최종 TPS
   - `context_clean`, `rate_limited`
   - 중계 로그의 `attempts`, `retry_schedule`
   - 유효하면서 평균이 1,354.66을 넘는 실행이 나오면 영상 검증과 제출 준비를 사용자와 함께 진행한다.
4. **열린 질문** (시간이 남을 때만)
   - 최종 호출의 빠른 상태(약 100ms)와 느린 상태(약 130–200ms)가 시간대나 부하에 따라 어떻게 바뀌는가
   - 첫 호출이 1,350 이상일 확률을 높일 방법이 있는가 (현재 24회 중 3회)

## 7. 주의사항

- 측정 조작 금지:
  - 응답을 바꾸지 않는다.
  - 중계 서버가 생성을 여러 번 보내고 가장 빠른 결과만 돌려주는 방식은 측정 조작이므로 쓰지 않는다.
  - 미리 캐시한 상품 결과는 실시간 조회 규칙 위반이다.
  - 상품을 프롬프트로 미리 지정하는 것은 운영진이 허용했다.
- **동시 세션 주의.** 다른 세션이 같은 게이트웨이와 중계 서버를 예약해 쓴 적이 있다(speed1500, `stop-requested`에 예약 문구).
- **중계 서버 파일을 고치면 버전 해시가 바뀐다.** 루프의 `relay_health()`와 speed1500 실행기가 해시를 확인하므로, 실행과 실행 사이 대기 중에 파일 교체와 서버 재시작을 함께 해야 한다.
- **커밋 방법.** 실행 기록 커밋(`ledger.py`, `git commit --only`)과 겹치지 않게, 루프가 결과를 쓴 직후 대기 시간에 지정 경로만 커밋한다. `SPEED1500-RESULTS.md`와 `.omo/`는 다른 세션 파일이다.
- **사용자 확인 사항.** Discord 제출, 공개 저장소 push, 실험 시작·중지는 사용자 확인 후에 한다.
- **API 키.** `profile.mjs`가 `~/.openclaw` 인증에서 메모리로만 읽는다. 파일이나 출력에 남기지 않는다.
