# 역대 최고 TPS를 재현하지 못한 원인 분석

2026년 11월 22일 · 기존 원본과 입력 이벤트의 사후 분석

**최근 기록에서 최종 호출 속도 하락과 재시도 중 입력 설정 유실을 확인했고, 새 상품 카드 실험은 출력 작업도 달랐다.** 서버 부하 하나의 원인으로 확정할 자료는 없다. 특히 최신 8회에서 재시도 경로가 짧은 시스템 입력과 선조회 조건을 유지하지 못한 구현 문제를 확인했다.

## 최고 기록을 만든 두 호출

| 실행 | 첫 호출 TPS | 최종 호출 TPS | 공식 평균 TPS |
|---|---:|---:|---:|
| D5009 · 이전 최고 | 809.90 | 1,792.65 | 1,301.28 |
| D5027 · 역대 최고 | 1,035.39 | 1,673.94 | 1,354.66 |
| D5050 · 같은 기준 설정의 최근 실행 | 971.54 | 796.12 | 883.83 |
| D5057 · 새 상품 카드 방식의 최고 | 827.90 | 1,302.55 | 1,065.23 |

D5027에서 D5050으로 평균이 470.84 TPS 낮아진 차이를 산술적으로 분해하면 첫 호출 기여는 −31.93, 최종 호출 기여는 −438.91 TPS다. 약 93%가 최종 호출 차이다. 첫 호출에 +100 TPS를 얻어도 두 호출 평균의 이득은 +50 TPS다. 최종 호출이 800 TPS대로 내려간 상황에서는 첫 호출 개선만으로 최고 기록을 넘기 어렵다. [D5027 원본 증빙](<../experiments/test/runs/cd75e5e0-be7c-471f-a9ab-c9e6f0d1bd77/evidence.json>) · [최근 같은 기준 실행](<../experiments/test/runs/1a14a3c4-24de-448e-b729-244976e05948/evidence.json>)

같은 기준 설정의 과거 유효 8회 평균 점수 중앙값은 962.09 TPS, 최근 유효 3회는 779.71 TPS다. 과거 최고 1,354.66도 당시 중앙값보다 약 41% 높았다. 최고 1회를 매번 기대할 수 있는 재현값으로 취급하기 어려운 분포다.

## 재시도에서 실험 조건을 고정하지 못했다

최신 플러그인은 원래 사용자 프롬프트 해시를 확인한 후 짧은 시스템 입력과 선조회 자료를 적용한다. OpenClaw의 복구 과정에서 프롬프트가 바뀌면 해시 검사가 실패했고, 호스트는 훅 오류를 기록한 뒤 기본 시스템 입력으로 진행했다. 실제 게이트웨이 로그에 `Manifest binding mismatch`가 52건 있으며, 실제 입력 이벤트에서도 설정 변경이 확인된다. 원래 요청을 확인하는 방어는 유지하면서 같은 실행의 복구 경로에도 실험 설정을 이어 주는 처리가 필요했다. 입력 이벤트는 시도 시점의 증거이며 생성 횟수와 같지 않다. D5056의 공식 점수는 실제 측정된 두 호출의 평균 719.15 TPS로 유지된다. D5055도 상품 답변은 맞지만, 짧은 시스템 입력과 선조회 조건만을 적용한 통제 비교로 보기 어렵다.

기존 보고서의 상품·답변 성공 6/8과 전체 공식 점수는 그대로다. 기존 `method_valid`는 재시도 전체의 입력 설정 유지까지 보장하지 못했다. 설정 유지가 확인된 두 쌍을 사후 진단하면 B의 공식 평균 우세는 1/2, 차이 중앙값은 +44.64 TPS다. 종전 3쌍·2승·+60.45는 설정 유실 실행을 포함한 과제 성공 기준의 관측값이다. 이 사후 분류는 조건 유실의 영향을 점검하기 위한 자료이며, 후보를 확정할 표본 수에는 부족하다. [이벤트 시각·해시와 분류](<TPS 최고 기록 미재현 원인 분석 - 2026-11-22.audit.json>)

이전 실험에도 복구 문맥 증가가 있었다. D5027의 계획 프롬프트는 943자였지만 네이티브 보고값은 1,303자, 같은 계획을 쓴 D5045는 2,659자였다. D5049도 계획 1,048자와 보고값 3,781자가 달랐다. 원래 시스템·도구 설명의 크기는 비슷했고, 내부 복구 지시와 앞선 요청이 실제 문맥에 추가돼 있었다. 해당 보고값은 훅 적용 전 단계도 포함하므로 최종 모델 입력 전체와 동일한 값으로 취급할 수 없다. 최신 8회는 실제 `llm_input` 이벤트로 설정 유실을 직접 확인했다.

## 새 상품 카드가 다른 출력을 요구했다

D5027은 이름과 링크의 161토큰 답변이었다. 새 방식의 성공 답변은 모두 1,890바이트이며 가격·재고·옵션까지 포함해 약 543–573토큰이었다. D5057 최종 호출은 543토큰을 416.88ms에 생성해 1,302.55 TPS였다. 토큰은 D5027보다 약 3.37배, 시간은 약 4.33배다. 답변을 길게 복사하면 TPS도 높아진다는 가정은 이번 측정에서 확인되지 않았다.

전용 도구가 절대 생성 시간을 줄인 사례도 있다. D5057의 첫 호출은 203토큰·245.20ms로 D5027의 447토큰·431.72ms보다 짧게 끝났지만, TPS는 827.90으로 낮았다. 입력이나 도구 인자가 작아지는 개선과 공식 TPS 상승은 각각 확인해야 한다.

정상 선조회로 한 번만 생성한 D5052·D5058도 1,049.71–1,059.62 TPS였다. 느린 조회 지시 호출을 없애는 데 성공했지만, 남은 생성 자체가 역대 최고 평균보다 느렸다. 최신 8회에는 같은 시간대의 D5027 원형 대조군이 없었고, 상품 카드와 도구도 함께 바뀌어 원래 구성 대비 전체 개선량을 분리할 수 없다. [8회 결과](<지정 선물 조회 구조 8회 실험 결과 - 2026-11-22.md>)

## 다음 실험에서 먼저 확인할 것

1. 재시도에서도 같은 실행 ID·세션과 원래 요청의 결합을 확인하고, 시스템 입력·도구 정책·선조회 자료가 유지되게 한다. 각 시도의 실제 입력 해시와 변경 여부를 남긴다.
2. 새 세션에서 D5027 원형과 변경 조건을 같은 시간대에 번갈아 실행한다. 상품과 최종 출력 형식을 맞춰 첫 호출과 최종 호출의 차이를 각각 계산한다.
3. 전체 전송·실패·원래 공식 점수를 모두 보존하면서, 재시도와 설정 유지 여부별 결과를 함께 보고한다. 출력 카드 확장과 최종 도구 정의 제거는 각각 따로 비교한다.

현재 우선순위는 재시도 경로의 설정 유실을 고치고 D5027 원형의 동시 대조값을 얻는 것이다. 최고치 재현 실패를 서버 상태나 추론량 하나로 설명할 근거는 부족하다.
