### Cerebras × Kimi K3.1 Pro TPS 최적화 방법론 조사

#### 1\. 핵심 결론

이번 TPS Bounty에서 가장 유망한 방법은 **Speculative Decoding에 유리한 출력 패턴을 찾아내고, 프롬프트·추론 설정·토큰 길이를 체계적으로 최적화하는 것**입니다.

Cerebras는 과거 Llama 3.1 70B 추론에 Speculative Decoding을 적용했으며, 그 결과 출력 속도가 평균 대비 약 ±20% 변동할 수 있다고 밝혔습니다. 하지만 **이번 Kimi K3.1 Pro 배포에도 동일한 방식이 적용되는지는 아직 확인되지 않았습니다.** 따라서 이 가설을 실제 API로 검증할 필요가 있습니다. [^r04][^r05]

행사 공식 안내는 TPS Bounty를 *가장 빠른 TPS를 달성한 프롬프트*에 수여한다고 명시합니다. 다만 평균·최댓값·서버 측 측정 중 어떤 것을 공식 점수로 사용할지는 공개된 안내만으로 확정할 수 없습니다. [^r06]

| 최적화 방향 | 기대 효과 | 공략 우선순위 |
|--------|--------|--------|
| 낮은 엔트로피의 출력 유도 | Speculative Decoding의 예측 적중률 향상 가능 | **1순위** |
| 반복·규칙적 패턴 생성 | 여러 토큰을 연속 예측하기 쉽게 구성 | **1순위** |
| 추론 강도 설정 비교 | 불필요한 추론 생성과 지연 축소 | 2순위 |
| 출력 토큰 길이 최적화 | 시작·종료 오버헤드의 영향 감소 | 2순위 |
| 프롬프트 길이·캐싱 | TTFT 및 전체 응답 시간 감소 | 3순위 |
| 동시 요청·배치 처리 | 전체 처리량 증가, 단일 요청 TPS는 별개 | 보류 |

여기서 중요한 점은 모델을 직접 개조하는 대회가 아니라는 것입니다. **서버 내부를 변경하지 않고도 프롬프트만으로 디코딩 성능을 얼마나 끌어올릴 수 있는지**가 가장 흥미로운 실험 대상입니다.

#### 2\. 실제 적용할 수 있는 6가지 방법론

##### 방법 A. Speculative Decoding의 예측 적중률 극대화

(가장 유망한 실험 가설)

Speculative Decoding은 작은 Draft 모델이 다음 여러 토큰을 미리 예측하고, 큰 Target 모델이 그 결과를 검증하는 방식입니다.

개념도: 실제 수용 개수와 속도 향상은 모델 및 서빙 엔진에 따라 달라집니다.

Red Hat은 코드, 구조화된 JSON, 반복 출력에서 Speculative Decoding의 성능 향상이 특히 유리하다고 설명합니다. [^r07]

더 흥미로운 점은 **Kimi K3.1 Pro에도 DSpark라는 전용 Speculative Decoding Draft 모델이 존재한다**는 사실입니다. AMD의 2026년 11월 기술 문서에서 실제 활용 사례가 확인됩니다. 이것이 Cerebras 환경에서도 활성화되어 있다는 증거는 아니지만, 실험 가설에 힘을 실어줍니다. [^r08]

따라서 다음 출력 유형을 비교해 보십시오.

- **동일 문자열 반복\:** `ALPHA BETA GAMMA DELTA`를 수백 회 반복
- **주기적 패턴\:** `A B C D A B C D ...`
- **구조화된 출력\:** 동일한 JSON 객체를 JSONL 형식으로 반복
- **일정한 코드 구조\:** 유사한 Python 함수나 SQL 구문 반복
- **비교군\:** 자유로운 에세이 또는 창의적 문장 생성

핵심은 단순히 같은 글자를 많이 출력시키는 것보다, **Draft가 여러 토큰을 연속으로 맞힐 만한 패턴을 찾는 것**입니다.

##### 방법 B. 토큰 분포의 엔트로피를 낮추기

다음 토큰을 예측할 때 가능한 후보가 적고 확률이 집중될수록 일반적으로 예측이 쉬워집니다.

예를 들어 다음 두 출력의 예측 가능성을 비교해 보십시오.

**낮은 엔트로피 후보** 예측 용이

```text
OK OK OK OK OK OK OK
OK OK OK OK OK OK OK
```

**높은 엔트로피 후보** 예측 어려움

```text
A4p 9Xq 2Lm 7Tr 5Zv
J8e 3Rc 6Bn 1Wy 4Kt
```

여기에는 두 가지 주의점이 있습니다.

첫째, 엔트로피가 낮아도 서버가 Speculative Decoding을 사용하지 않는다면 큰 속도 향상으로 이어지지 않을 수 있습니다.

둘째, 사람이 보기에 짧은 문자열이라고 해서 토큰 수가 적거나 많은 것은 아닙니다. Kimi의 토크나이저를 사용하여 실제 토큰 분할을 확인하고, 최종적으로는 API의 `completion_tokens`를 기준으로 비교해야 합니다.

추가로 Kimi K3.1 Pro는 896개의 라우팅 전문가 중 토큰당 16개를 선택하는 MoE 구조입니다. 이 때문에 입력 및 출력 패턴에 따른 전문가 라우팅도 성능 변동을 설명할 수 있는 후보 요인입니다. 다만 이를 사용자가 직접 제어할 수 있다는 근거는 없습니다. [^r09]

##### 방법 C. Reasoning Effort 실험

Kimi K3.1 Pro에서 실제로 조정할 수 있는 중요한 변수입니다.

비교할 설정 해커톤 모델 지원 여부 확인

추론을 줄이면 출력 시작까지의 시간이 단축될 가능성이 있습니다. 그러나 **초당 생성 토큰 수 자체가 반드시 높아지는 것은 아닙니다.**

또한 내부 reasoning 토큰이 전체 `completion_tokens`에 포함되면, 화면에 나타나는 답변 길이만으로 TPS를 계산하는 것은 잘못입니다. Nebius의 Kimi K3.1 Pro 실험에서도 reasoning 수준에 따라 생성 토큰 수가 달라지는 것을 확인할 수 있습니다. [^r10]

##### 방법 D. 출력 길이 최적화

출력 길이는 512, 2,048, 4,096, 8,192토큰 수준으로 단계별 비교를 권합니다.

짧은 요청에서는 네트워크와 응답 시작 오버헤드가 두드러집니다. 긴 요청에서는 이를 분산시킬 수 있지만 컨텍스트 증가, 부하 변동, 모델의 조기 종료 등이 새로운 영향을 줍니다.

**`max_completion_tokens`를 크게 설정했다고 실제로 그만큼 출력하는 것은 아닙니다.** 실제 생성 토큰 수와 종료 사유를 기록해야 합니다.

##### 방법 E. 프롬프트 캐싱과 Prefill 최소화

Cerebras의 Prompt Caching은 이전에 처리한 프롬프트 접두부를 재사용하여 TTFT를 낮추는 방식입니다. [^r11]

실험에서는 불필요한 긴 시스템 프롬프트, 도구 정의, 이전 대화를 줄이고 가능하면 같은 조건에서 비교하십시오.

하지만 캐싱이 개선하는 핵심은 주로 입력 처리 시간입니다. **Prefill이 빨라지는 것과 Decode TPS가 높아지는 것은 구별해야 합니다.**

##### 방법 F. API·서빙 최적화

하드웨어나 서버 설정을 직접 관리할 수 있다면 더 많은 기술이 있습니다.

| 기술 | 효과 | 이번 대회 적용성 |
|--------|--------|--------|
| Speculative Decoding | 토큰 검증 단계 감소 | 서버 설정 권한 없음, 프롬프트로 간접 공략 |
| Prefix / KV Cache | 중복 입력 연산 감소 | 일부 활용 가능 |
| Continuous Batching | 다중 요청 처리량 개선 | 단일 요청 TPS 부문에서는 우선순위 낮음 |
| Quantization | 메모리 대역폭·연산 부담 감소 | 모델 서빙 권한 필요 |
| Kernel Fusion / Graph Capture | 실행 오버헤드 감소 | 서버 측 최적화 |
| Predicted Outputs | 알려진 출력 부분을 활용 | 해커톤 전용 모델 지원 여부 미확인 |

이 중 실제로 집중해야 할 것은 **프롬프트 설계에 따른 Decode 경로의 변화**입니다. 참고로 Cerebras의 Predicted Outputs 기능은 일반적인 프롬프트 최적화와 다른 기능이며, 별도 지원 여부와 대회 허용 여부를 확인해야 합니다. [^r12]

#### 3\. 가장 중요한 부분: TPS 측정 방법

측정 정의에 따라 우승 전략 자체가 달라집니다.

기록해야 할 세 가지 성능 지표

마지막 식은 토큰별 도착시각을 알 때의 근사식입니다. SSE 청크 개수를 토큰 개수로 취급해서는 안 됩니다.

Cerebras API는 응답에 `usage.completion_tokens`와 `time_info.completion_time` 등의 정보를 제공합니다. 서버 측 측정값과 클라이언트의 실제 경과시간을 함께 수집하는 것이 좋습니다. [^r13]

또한 **단일 요청 TPS와 여러 요청의 합산 TPS는 다른 지표**입니다. 이번 상이 프롬프트별 속도를 겨루는 만큼, 동시 요청으로 처리량을 키우는 방법을 우선 공략할 이유는 적습니다.

#### 5\. 바로 사용할 수 있는 벤치마킹 코드

공식 Cerebras Python SDK를 이용한 최소 실험 코드입니다. 현재 공개된 해커톤 안내의 모델 ID를 사용하지만, 실제 실행에는 해당 모델의 프리뷰 접근 권한이 필요합니다.

```python

# pip install cerebras_cloud_sdk
import os
import time
import csv
from cerebras.cloud.sdk import Cerebras

MODEL = "moonshotai-kimi-k3.1-pro-trial"

client = Cerebras(
    api_key=os.environ["CEREBRAS_API_KEY"],
    max_retries=0,
)

prompts = {
    "repeat": (
        "Write exactly 250 lines. "
        "Each line must be: ALPHA BETA GAMMA DELTA. "
        "Do not abbreviate or summarize."
    ),
    "cycle": (
        "Continue this A B C D cycle for 2000 symbols, "
        "separated by spaces. No explanations."
    ),
    "jsonl": (
        'Write 250 JSONL lines. Each line exactly: '
        '{"ok":true,"value":0,"tag":"alpha"} '
        "Do not abbreviate or summarize."
    ),
    "baseline": (
        "Write a detailed original essay about "
        "how AI changes scientific research."
    ),
}

records = []

for name, prompt in prompts.items():
    for repeat in range(5):
        start = time.perf_counter()

        r = client.chat.completions.create(
            model=MODEL,
            messages=[{"role": "user", "content": prompt}],
            reasoning_effort="low",
            max_completion_tokens=4096,
        )

        wall = time.perf_counter() - start
        data = r.to_dict()
        usage = data.get("usage") or {}
        timing = data.get("time_info") or {}

        tokens = usage.get("completion_tokens", 0)
        decode_s = timing.get("completion_time")

        record = {
            "name": name,
            "repeat": repeat,
            "tokens": tokens,
            "decode_tps": (
                tokens / decode_s if decode_s else None
            ),
            "wall_tps": tokens / wall,
            "finish_reason": data["choices"][0]["finish_reason"],
        }
        records.append(record)
        print(record)

with open("tps_results.csv", "w", newline="") as f:
    writer = csv.DictWriter(
        f, fieldnames=records[0].keys()
    )
    writer.writeheader()
    writer.writerows(records)
```

이 코드는 **실측 전 실험 도구**이며, 여기서 특정 프롬프트의 우수한 TPS가 확인된 것은 아닙니다. API가 특정 추론 설정을 거절하거나 `time_info`를 반환하지 않으면 해당 조건을 조정해야 합니다.

또한 해커톤 공식 FAQ에서는 OpenClaw 사용을 필수로 규정합니다. 따라서 API로 성능을 탐색한 뒤 최종 결과물에서도 OpenClaw 하네스 사용 조건을 충족해야 합니다.

##### B. 하이브리드 Attention: 컨텍스트 길이의 영향

Kimi K3.1 Pro의 93개 계층은 다음과 같이 구성됩니다.

Attention 계층 구성 총 93개

KDA 69개 (74.2%)

Gated DSA 24개 (25.8%)

- **KDA\:** 고정 크기의 순환 상태를 사용하기 때문에, 전체 과거 토큰을 매번 직접 탐색하는 일반 Attention과 다릅니다.
- **Gated DSA\:** 인덱서가 전체 문맥을 검사하지만 실제 Attention은 중요한 상위 2,048개 토큰을 선택합니다.

이 구조는 긴 문맥의 Decode 비용 증가를 억제합니다. 그렇다고 긴 프롬프트가 더 빠르다는 의미는 아닙니다. DSA 인덱서의 탐색 비용과 상태 관리 비용은 여전히 남습니다. [^r18][^r15]

**H2: 짧은 컨텍스트에서는 거의 일정한 Decode TPS를 보이고, 긴 컨텍스트에서는 성능이 점진적으로 저하될 수 있다.**

이를 검증하려면 동일한 출력 작업에 대해 입력만 256, 2,048, 8,192, 32,768토큰으로 늘려 비교하면 됩니다.

##### C. MoE Expert Routing: 토큰 패턴별 실행 비용

Kimi는 계층별로 896개 Routed Expert 가운데 16개를 선택하고 2개의 Shared Expert도 사용합니다. [^r19]

여기서 흔히 하는 잘못된 추측이 있습니다.

> 동일한 토큰을 반복하면 활성화되는 Expert 수가 줄어들어 계산량이 감소할 것이다.

이것은 근거가 부족합니다. **일반적인 추론에서 선택되는 Routed Expert 수는 16개로 고정**되어 있기 때문입니다.

대신 토큰 종류에 따라 선택된 Expert의 분포가 달라지고, 내부 스케줄링이나 데이터 이동이 바뀔 가능성은 있습니다. 다만 Cerebras가 이를 어떻게 최적화하는지는 공개 자료만으로 파악할 수 없습니다.

따라서 MoE 라우팅은 실험할 가치는 있지만, 1순위 최적화 수단으로 보기는 어렵습니다.

#### 3\. Cerebras에 맞춘 실험 우선순위

제안하는 실험은 다음과 같습니다.

| 실험 | 통제·변경 변수 | 확인하려는 것 | 우선순위 |
|--------|--------|--------|--------|
| A | 수학 / 코드 / JSON / 반복 출력 | Speculative Decoding 친화적인 출력 발견 | **최상** |
| B | 256\~32K 입력 컨텍스트 | KDA·DSA의 길이 의존 성능 | 높음 |
| C | reasoning `low/high/max` | 추론 모드별 Decode TPS 차이 | 높음 |
| D | 출력 512\~8K토큰 | 측정 안정성과 출력 길이 효과 | 높음 |
| E | 숫자·영어·기호 패턴 | 토큰 구성 및 Expert Routing의 간접 영향 | 중간 |

Kimi K3.1 Pro의 샘플링 파라미터는 일반적으로 `temperature=1.0`, `top_p=0.95`로 고정되어 있습니다. 추론 강도는 제공자에 따라 세부 지원값이 달라지므로, 대회 엔드포인트에서 실제 허용값을 확인해야 합니다. [^r20]

#### 4\. TPS를 어떻게 측정해야 하는가

Cerebras API에는 다른 서비스와 구별되는 유용한 측정 정보가 있습니다.

```json
{
  "time_info": {
    "queue_time": 0.01,
    "prompt_time": 0.03,
    "completion_time": 1.20,
    "total_time": 1.24
  }
}
```

예시 수치이며 실제 측정 결과가 아닙니다. Cerebras 공식 API의 응답 필드 구조를 따른 것입니다. [^r21]

여기서 가장 먼저 봐야 할 것은 다음 지표입니다.

\[
TPS_{\text{decode}}=
\frac{\text{completion\_tokens}}{\text{completion\_time}}
\]

다만 공식 운영진이 이 지표를 채점에 사용하는지는 별도로 확인해야 합니다.

한 가지 더 주의할 점은 `completion_tokens`에 숨겨진 Reasoning 토큰도 포함될 수 있다는 것입니다. 따라서 실제 화면 출력 토큰과 전체 생성 토큰을 분리하여 기록하십시오.

##### 권장 실험 진행 순서

1. **성능 기준선 수립**
   
   별다른 최적화 없이 1,024\~2,048토큰을 생성하여 기본 TPS 범위를 파악합니다.
2. **출력 패턴 탐색**
   
   출력 길이와 Reasoning 설정을 통제하고 수학, 코드, 반복 문자열, JSON 생성의 TPS를 비교합니다.
3. **컨텍스트 길이 및 추론 강도 최적화**
   
   상위 패턴만 선정하여 입력 길이와 Reasoning 설정을 변경합니다.
4. **최종 재현성 검증**
   
   상위 후보를 무작위 순서로 10회 이상 반복하고 TPS 중앙값, 최고값, 표준편차를 확인합니다.

실험 시 서버 부하의 영향을 줄이기 위해 요청은 순차적으로 실행하고, `queue_time`이 비정상적으로 높은 결과는 따로 표시하는 것이 좋습니다.

#### 5\. 제가 가장 주목하는 실험

세 가지 프롬프트를 동일 조건으로 비교하는 것입니다.

**후보 A — 수학적 추론 패턴** DSpark 가설

간단한 산술 문제 100개를 번호, 계산 과정, 정답 형식으로 연속 풀이하도록 지시합니다.

**후보 B — 규칙적인 코드 생성** 구조적 예측성

비슷한 형태의 데이터 검증 함수를 여러 개 생성하고, 각 함수가 일정한 문법을 따르도록 합니다.

**후보 C — 일정 문자열 반복** 저엔트로피 비교군

고정된 4\~8개 단어의 반복 시퀀스를 가능한 한 안정적으로 생성하도록 지시합니다.

예상 결과를 섣불리 단정해서는 안 됩니다. 수학 패턴이 높을 수도 있고, 반복 패턴이 높을 수도 있으며, 거의 차이가 없을 수도 있습니다. 특히 마지막 결과가 나온다면 해당 Cerebras 엔드포인트에서는 프롬프트의 예측 가능성보다 서버 측 고정 Decode 시간이 더 지배적일 가능성을 생각해 볼 수 있습니다.

**Cerebras에 맞는 TPS 최적화는 GPU에서처럼 메모리 사용량을 줄이는 작업이 아니라, 실제 배포된 추론 엔진의 토큰 생성 특성을 역으로 찾아내는 작업**이라고 보는 것이 적절합니다.

또한 DSpark는 Kimi 본체의 중간 계층에서 얻은 Hidden State를 활용합니다. 따라서 단순히 문자 반복을 쉽게 만드는 것보다 **Kimi 본체와 Draft 모델이 다음 토큰을 비슷하게 예측하는 상태를 유도하는 것**이 기술적으로 더 중요한 목표입니다.

##### 제가 새로 제안하는 가설

**최근 2,048토큰 안에서 일관된 출력 구조를 유지하면서, 모델이 익숙한 산술·코드 생성 패턴을 사용하는 것이 유리할 수 있습니다.**

이것은 DSpark의 Sliding Window 설계에서 도출한 실험 가설입니다. 긴 문맥 전체를 활용하는 것보다 가까운 문맥의 명확한 생성 패턴을 활용하는 실험을 우선하자는 뜻입니다.

단, Cerebras가 해당 DSpark를 사용하지 않는다면 이 가설은 TPS 개선과 직접 연결되지 않을 수 있습니다.

#### 3\. Kimi의 특성을 실제 최적화로 연결하는 방법

##### 전략 A. DSpark의 최근 2,048토큰 문맥 활용

제가 가장 먼저 시험하고 싶은 방법입니다.

새 DSpark의 Draft 계층은 최근 2,048토큰에 Attention을 수행합니다. 그렇다고 오래된 정보가 완전히 사라지는 것은 아닙니다. Kimi 본체에서 전달되는 Hidden State에는 더 긴 문맥의 정보가 반영될 수 있습니다. [^r25]

이를 활용해 출력의 규칙성이 유지되는 범위를 조절해 보십시오.

| 실험 | 출력 구조 | 검증 가설 |
|--------|--------|--------|
| A1 | 동일 문장 연속 반복 | 단순한 다음 토큰 예측 |
| A2 | 4\~8개 문장 주기적 반복 | 짧은 국소 패턴 활용 |
| A3 | 유사한 구조의 코드 함수 연속 생성 | 학습된 코드 문법 활용 |
| A4 | 동일한 산술 계산 형식 반복 | 산술 추론 패턴 활용 |
| A5 | 2,048토큰을 넘는 긴 패턴 반복 | Draft의 지역 문맥 의존성 확인 |

특히 A3와 A4를 A1에 대조하는 것이 중요합니다.

**단순 반복보다 Kimi가 잘 학습한 생성 구조가 빠르다면**, 적어도 해당 환경에서는 낮은 엔트로피보다 모델과 Draft의 예측 일치성이 더 유용하다는 근거가 됩니다.

##### 전략 B. Reasoning Effort를 단순히 최소화하지 말고 비교

Kimi K3.1 Pro는 기본적으로 추론 기능을 사용합니다.

Cerebras의 2026년 11월 문서 업데이트에 따르면 Kimi K3.1 Pro에 `low`, `medium`, `high`, `max`가 지원되며 기본값은 `max`입니다. 단, 해커톤 전용 `trial` 모델도 네 가지를 모두 지원하는지는 직접 확인이 필요합니다. [^r26]

| 설정 | 검증할 가설 |
|--------|--------|
| `low` | 불필요한 추론 토큰을 줄여 전체 지연을 단축 |
| `medium` | 짧은 추론과 구조적 출력의 균형 |
| `high` | 모델의 안정적인 추론 패턴이 TPS를 높이는지 |
| `max` | 긴 추론 출력이 오히려 높은 Decode TPS를 달성하는지 |

여기서 중요한 차이는 **응답이 빨리 끝나는 것과 TPS가 높은 것은 같지 않다**는 점입니다.

예를 들어 `max`가 많은 추론 토큰을 빠르게 생성한다면 Decode TPS는 높게 나올 수 있습니다. 반대로 복잡한 추론이 Speculative Decoding의 예측 일치율을 낮추면 TPS가 떨어질 수도 있습니다.

`temperature=0`으로 강제로 결정적 출력을 만드는 전략은 우선 제외하겠습니다. Kimi K3.1 Pro는 제공자에 따라 샘플링 파라미터가 고정되어 있으며, Moonshot 계열 API는 일반적으로 `temperature=1.0`, `top_p=0.95`를 사용합니다. [^r27]

##### 전략 C. DSA를 고려한 짧은 입력과 긴 출력의 균형

Kimi K3.1 Pro의 DSA는 중요한 과거 토큰 2,048개에만 본격적인 Attention을 수행합니다. 그러나 **중요한 토큰을 찾는 Indexer는 그보다 긴 전체 과거 문맥을 탐색**합니다. [^r28]

따라서 최대 100만 토큰을 지원한다는 이유로 긴 문맥을 주는 것은 TPS 경쟁에 유리하지 않습니다.

첫 실험은 256\~1,024토큰 안팎의 입력에서 시작하고, 최종 후보에 대해서만 2,048·8,192토큰 입력을 비교하겠습니다.

출력 길이도 중요합니다. 출력이 길어질수록 생성된 토큰 자체가 문맥에 추가되므로, Decode TPS가 출력 전반에 걸쳐 일정한지 확인할 필요가 있습니다.

##### 전략 D. MoE 라우팅은 후순위로

Kimi는 토큰마다 16개 Routed Expert를 활성화합니다. 반복 문자열을 생성한다고 해서 그 수가 자동으로 줄어드는 것은 아닙니다.

Cerebras에서 전문가별 실행 비용이나 라우팅 패턴에 차이가 있을 가능성은 있지만, 공개 API만으로 내부 Expert 사용량을 관찰하거나 선택을 제어할 수는 없습니다.

따라서 영어·숫자·코드·JSON 출력 사이의 차이를 관측할 수는 있어도, 이를 곧바로 Expert Routing 효과로 해석해서는 안 됩니다.

Each function accepts x and returns

코드 문법은 일정하고 일부 숫자만 달라지는 구조입니다.

{"id":1,"status":"ok","value":100}

Output JSONL only.

고정된 토큰 배열과 바뀌는 숫자가 혼합된 형태입니다.

**P4. 순수 저엔트로피 반복** 비교군

```text
Repeat the exact sequence below 300 times:

ALPHA BETA GAMMA DELTA

Write the full sequence each time.
Do not abbreviate, count, or summarize.
```

산술이나 코드에 비해 실제로 빨라지는지 확인하는 핵심 비교군입니다.

모델이 지시된 줄 수를 정확하게 생성하지 않을 수도 있습니다. 따라서 출력의 완전성과 실제 생성 토큰 수를 함께 기록해야 합니다.

토크나이저와 MoE 라우팅에 따른 성능 차이 가능성을 탐색하되, 내부 원인을 섣불리 단정하지 않습니다.

#### 7\. 중요한 일정과 실행 판단

해커톤 공식 안내상 Cerebras Org ID 제출 마감은 **한국 시간 11월 21일 토요일 정오**, 대회 시작은 **11월 22일 일요일 오전 3시**입니다. Org ID를 제출하지 않으면 Kimi K3.1 Pro 프리뷰 모델에 대한 접근 권한을 받지 못할 수 있으니 신청 완료 여부를 반드시 확인하십시오. [^r30]

모델 이용 권한을 받은 뒤에는 우선 P1\~P4의 TPS를 비교하고, 가장 빠른 두 후보에서 `reasoning_effort`와 출력 길이를 교차 실험하는 것이 효율적입니다.

**저는 P1(산술 패턴)과 P2(코드 생성)를 1차 우승 후보로, P4(문자열 반복)를 비교군으로 잡겠습니다.** DSpark 벤치마크를 근거로 한 선택이지만 Cerebras에서 반드시 이 순서로 빠르다는 뜻은 아닙니다.

마지막으로 운영진에게는 \*“해커톤 Kimi 엔드포인트에서 Speculative Decoding을 사용하고 있는가?”\*와 \*“TPS를 어떤 공식으로 채점하는가?”\*를 확인하는 것이 좋겠습니다. 이 두 답변만으로도 실험 방향을 크게 좁힐 수 있습니다.

이 접근의 가장 큰 장점은 단순히 수상용 프롬프트를 만드는 데 그치지 않고 **모델 아키텍처를 해석하고, 성능 가설을 세우고, 측정을 통해 검증하는 작업**이라는 점입니다.
